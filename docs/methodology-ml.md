# Обучаемый прогноз спроса

## Что изменилось

До этой работы `app/engine/forecast.py` был статистическим прогнозом: среднее, сезонность с усадкой и линейный тренд. Обучения отдельной ML-модели, сохраненного артефакта и временной проверки не было. `app/copilot.py` объясняет готовые числа; он не прогнозирует спрос.

Добавлен `app/ml/model.py`: общая для IEK и SE модель `HistGradientBoostingRegressor` из scikit-learn. В отличие от отдельной модели на каждый SKU, она использует примеры разных товаров; по одному товару слишком мало полных месяцев. Это градиентный бустинг по деревьям, не LLM. [Документация алгоритма](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html).

## Признаки и цель

- Единица примера: товар, последний известный полный месяц, будущий месяц через 1–3 месяца.
- Признаки: продажи 1/2/3/6/12 месяцев назад, средние за 3/6 месяцев, доля ненулевых месяцев, изменчивость, масштаб товара, месяц года, поставщик, категория, единица измерения и прогноз статистического метода с его сезонным/трендовым коэффициентами.
- Числовые объёмы нормированы на среднее за предыдущие 12 месяцев, минимум 1. Так метры и штуки разных масштабов не суммируются как сопоставимые величины.
- Цель: наблюдавшиеся продажи за полный месяц за вычетом разового избытка. В обучение/оценку входят месяцы с положительным начальным остатком. Добавленная оценка потерянного спроса не используется как известная целевая величина. Историческая коррекция дефицита участвует в признаках.
- Сравниваются Poisson и absolute error с одинаковыми фиксированными параметрами: 150 итераций, 15 листьев, learning rate 0.05, min_samples_leaf 30, L2=10, seed=42. Ранняя остановка по случайной выборке отключена. Выбирается меньшая ошибка на двух ранних временных срезах.
- Выбран `absolute_error`: его точечный прогноз соответствует типичному/медианному объёму, а не гарантированному математическому ожиданию спроса. Исторический страховой запас не является калиброванным доверительным интервалом этой модели.

## Защита временной проверки от утечек

Для каждого конца месяца заново выполняются поиск разовых продаж и обработка дефицита только на доступном префиксе накладных и остатков. Нельзя очистить весь набор один раз, а затем разделить его на обучение и проверку: будущие накладные изменили бы медианы и решение о повторяемости опта.

Признаки обрезают также месячный отчет. Внешние коэффициенты сезонности компании не датированы, поэтому в ML и его статистическом эталоне заменены нейтральным профилем; сезонность SKU/группы обучается на доступной истории. Текущий остаток, будущие поставки, заказ менеджера и его коэффициенты не являются признаками спроса.

Проверочные моменты: март, апрель и май 2026, прогноз на следующие 1–3 месяца. Для каждого момента обучающие целевые месяцы не позже этого момента. Выбор функции ошибки использует первые два среза, с целями не позднее июля; последний месяц проверки — август, прогноз из мая. Части горизонтов пересекаются, поэтому общий результат не является тремя независимыми тестами. Первоначальный пробный Poisson также оценивался на всех срезах; августовый результат не следует представлять как совершенно нетронутый внешний тест исследовательского процесса.

## Полученные результаты на реальных Excel

Финальная модель обучена по август 2026 включительно: **86 094 примера, 2 523 товара**. Сентябрь неполный и не используется как целевой месяц обучения. Машиночитаемый отчет: [ml-evaluation.json](ml-evaluation.json).

Основная метрика: среднее `abs(прогноз − очищенные продажи) / max(предыдущее среднее товара за 12 месяцев, 1)`. Она безразмерна, меньше — лучше; это не «процент точности».

| Проверка | Статистика | ML | Снижение ошибки |
|---|---:|---:|---:|
| Мартовский срез | 0.8711 | 0.7025 | 19.36% |
| Апрельский срез | 0.9638 | 0.8125 | 15.69% |
| Майский срез | 0.9817 | 0.8394 | 14.50% |
| Все 20 507 проверочных примеров | 0.9389 | 0.7849 | 16.41% |
| Август отдельно, 2 274 примера | 0.9783 | 0.8203 | 16.15% |

WAPE считается отдельно внутри поставщика/единицы: сумма абсолютных ошибок / сумма наблюдавшихся количеств. Для IEK в штуках WAPE ухудшился с 33.72% до 35.93%, хотя нормированная ошибка по товарам улучшилась. Для SE в штуках WAPE снизился с 40.04% до 31.00%; для IEK в метрах — с 60.71% до 47.76%. Поэтому ML не объявлен лучшим для каждого товара и остается явным выбором пользователя.

## Подключение к продукту

```powershell
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m app.adapters.build --raw datasets
.venv\Scripts\python.exe -m app.ml.train
.venv\Scripts\python.exe -m streamlit run app/ui/app.py
```

Выбрать «Метод прогноза → ML — обученный бустинг», затем «Рассчитать». В коде: `run(data, Params(forecast_method="ml"))`.

Сохраняются `data/models/demand.joblib` и `demand.json` с параметрами, периодом обучения, версиями, SHA256 исходных parquet и результатами проверки. Они локальны и исключены из Git; teammates воспроизводят модель командой обучения. Загружать произвольные чужие joblib-файлы небезопасно: интерфейс не принимает такие загрузки. После изменения данных/версии scikit-learn модель необходимо переобучить; исторический расчет раньше конца обучения отклоняется.

ML заменяет `forecast_H`, прогнозируя месяцы отдельно. На неполный месяц используется пропорция будущих дней. Рост категории применяется один раз после ML; остатки, товар в пути, округление и утверждение остаются в прежнем модуле пополнения. Для месяцев дальше третьего применяется явно помеченный статистический прогноз. В карточке показаны месячные значения обоих методов, в шапке — метод и проверка качества. Семь отключений факторов во вкладке «Проверки» относятся к статистическому методу и так подписаны.

## Ограничения и следующий эксперимент

Положительный остаток в начале месяца не доказывает наличие товара весь месяц; истинный неудовлетворённый спрос неизвестен. История короткая, новые товары и изменения ассортимента отражены не полностью. Данные за 2024 и накладные расходятся по составу, поэтому отчет используется в статистических признаках осторожно. Категории/единицы из каталога считаются постоянными во времени.

Следующий этап: получить историю поступлений и ежедневной доступности; проверить прогноз на новых месяцах после сентября без повторного выбора параметров; оценить ошибки с весами стоимости и дефицита, обучить квантили под уровень сервиса. До этого нельзя обещать снижение фактического дефицита/затрат только на основании MAE.
