# Методика: ассистент и жизненный цикл ассортимента

Код: `app/engine/lifecycle.py` (сигналы), `app/assistant.py` (поиск, проверка пар, рекомендации), `app/ui/tab_assistant.py`.

## Сигналы жизненного цикла (без ИИ, детерминированно)

По регулярному месячному спросу полных месяцев (`DEMAND_MONTHLY.qty_regular`):

- **Угасающий спрос** — среднее за последние 3 месяца < 25% среднего за 9 месяцев до них при базе ≥ 3 ед./мес. База прогноза — 12 месяцев, поэтому такой товар всё ещё получает рекомендацию к заказу: риск излишков. На реальных данных — 128 позиций, из них 38 с рекомендацией к заказу.
- **Новинка** — пометка «NEW» в названии или первая продажа в последние 12 месяцев (и продажи в последние 3 месяца). Короткая история — прогноз ненадёжен. Новинка не помечается угасающей: её первые месяцы — запуск, а не база. 144 позиции.
- **Кандидат в замену** — угасающий товар и новинка того же поставщика и товарной группы с похожими названиями (сходство ≥ 0.6), либо точное совпадение названия у всего поставщика (перекодировка). Предварительный вердикт: одинаковое название → «та же позиция под новым кодом»; различаются числовые параметры (ток, сечение, число клавиш) → «вероятно вариант исполнения»; иначе «не проверено». На реальных данных 33 пары: 29 — вероятные варианты, 4 — требуют проверки; подтверждённых замен нет.

Сигналы **не меняют количества**. Они добавляются в `flags` (`lifecycle:declining`, `lifecycle:new_item`, `lifecycle:replaced_by:<код>`) и одним предложением с рекомендацией в обоснование строки. Замена попадает в строку заказа только подтверждённой: одинаковое название или вердикт ИИ «замена модели».

## ИИ (ChatGPT API), если задан `OPENAI_API_KEY`

- **«Спросить ассистента» — свободный вопрос.** (1) Модель по строгой JSON-схеме выбирает намерение (список позиций / объяснение товара / сводка поставщика / рекомендации / жизненный цикл) и фильтр. (2) Приложение берёт данные из расчета: до 15 строк заказа с ключевыми числами, сводку поставщика, рекомендации или итоги по ассортименту. (3) Модель пишет ответ только по этим данным. Каждое число ответа проверяется: оно должно быть в данных или в вопросе (с точностью округления). Иначе показывается шаблонный ответ и таблица. Под ответом всегда видна таблица строк, на которых он основан. Проверено на реальных данных с `gpt-4o-mini`: «почему по трубе Ø50 такой заказ», «сводка по SE», «что сделать с заказом», «есть ли товары, выходящие из ассортимента».
- **Вердикт ИИ по паре не отменяет параметры.** И `gpt-4o-mini`, и `gpt-4.1-mini` на реальных парах ошибочно называли «заменой» товары с разными параметрами (колодка на 3 вывода против 2 уровней, рамка на 4 места против 1). Поэтому «замена» от ИИ принимается, только если числовые параметры названий совпадают; иначе остается «вариант исполнения» с пометкой.

- **Поиск обычными словами.** Модель получает только текст запроса и возвращает фильтр строго по JSON-схеме: поставщик, срочность, 1–3 слова названия, признаки (дефицит, разовые продажи, сезонный пик, в пути, жизненный цикл), сортировка. Приложение проверяет и применяет фильтр. Количеств модель не видит и не создаёт. Без ключа или при ошибке — разбор по ключевым словам.
- **Проверка пар «старая → новая модель».** Модель читает названия и выбирает вердикт (замена / вариант исполнения / не связаны) и причину из фиксированных списков. Свободного текста нет. Без ключа остаётся предварительный вердикт.
- **Объяснение строки и сводка поставщика** — `app/copilot.py`: модель выбирает факты из каталога, составленного приложением.

Внешних источников о выходе новых моделей (сайты производителей, каталоги) в MVP нет: вывод «вышла новая модель» строится только по выгрузкам партнёра и названиям. Подключение каталога производителя — развитие после хакатона.

## Рекомендации

Детерминированный список по текущему заказу (с правками менеджера): критичные позиции по поставщикам, угасающие позиции с заказом, новинки в заказе, оценочные остатки IEK, сезонный пик, пары на проверку.
