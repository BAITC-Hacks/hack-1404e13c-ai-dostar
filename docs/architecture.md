# SupplyAI — архитектура MVP на 4 часа

Дата: 23.09.2026. Основание: кейс ТОО «Электрокомплект», реальные выгрузки IEK и Systeme Electric (SE), проектный документ `SupplyAI_ARCHITECTURE.md` (далее «полная архитектура»).

Полная архитектура — целевое состояние продукта. Её доменные правила (разделы 4.1, 5.1, 5.2, 6.2) приняты здесь почти без изменений. Её инфраструктура (3 микросервиса, 3 БД, очередь заданий, auth, идемпотентность, CatBoost, два LLM-провайдера) на хакатон **не переносится**: 3 человека × 4 часа её не соберут, а жюри проверяет 5 must-have, а не отказоустойчивость.

## 1. Решение

Модульный монолит на Python. Без БД: parquet-файлы + состояние в памяти/JSON.

| Слой | Стек | Папка | Владелец |
|---|---|---|---|
| Адаптеры данных (готово) | pandas, calamine | `app/adapters/`, `python -m app.adapters.build` | A |
| Контракт | dataclass/колонки | `app/schema.py` | все, менять только вслух |
| Движок расчета | pandas, numpy | `app/engine/`, `app/pipeline.py` | B |
| UI | Streamlit | `app/ui/` | C |
| LLM-объяснение (опционально) | один провайдер, шаблон как fallback | `app/copilot.py` | C или B после 3:00 |
| Тесты приемки | pytest | `tests/` | A |

Если в команде есть готовый React-шаблон и уверенный фронтендер — допустимо FastAPI + React, но движок остается тем же модулем, а API — тонкой оберткой над `pipeline.run`. По умолчанию Streamlit.

## 2. Реальные данные и расхождения с контрактом

По папке на поставщика: `IEK/`, `Systeme electric/`. Сырые файлы лежат в `data/raw/` и не коммитятся. Имена файлов в zip в cp866: `unzip -O cp866`.

| Файл | Содержимое | Канонская таблица |
|---|---|---|
| Динамика продаж | Строки накладных: Дата, Номер, Документ, Код, Номенклатура, Ед., Склад, Количество | `sales_lines` |
| Ежемесячные продажи | SKU × месяц, 01.2024–09.2026 | `monthly_sales` |
| Ежемесячные остатки | Начальный остаток SKU × месяц, 01.2024–09.2026 | `stock_monthly` |
| MOQ | IEK «Мин. разр. к отгр.», SE «Кратность» | `products.pack_multiple` |
| Путь ИЭК | Колонка на заказ поставщику, в заголовке дата заказа и «поступление до» | `in_transit` |
| Товар в пути SE | Фактически **текущий Excel-расчет менеджера**: ср. за 12 мес, Кэф. Роста, Кэф. Сез-ти, остатки по складам, резерв, свободный остаток, Запас, Заказ (пуст), «СЭ в пути» | `stock_now`, `in_transit`, `products.category`, эталон для сравнения |
| Сезонность | Помесячные коэффициенты компании (в деньгах) | `company_seasonality` |

Чего нет по сравнению с ТЗ и полной архитектурой, и как мы это закрываем:

| Нет в данных | Решение MVP | Отразить в README |
|---|---|---|
| client_id, цена | Единица анализа выбросов — строка накладной (`doc_id` + SKU) | «крупная продажа одному клиенту» ≈ крупная строка одной накладной |
| Периоды stockout | Месяц с нулевым/отсутствующим начальным остатком = stockout-месяц (у IEK 29% SKU-месяцев) | Гранулярность месячная, `availability_known=false` |
| Справочник поставщиков, lead time | Поставщик = папка. Lead time — параметр (дефолт 30 дн.); ориентир из «Путь ИЭК»: 12–40 дней | Параметр в UI |
| Материальная ведомость (BOM) | Не используется | Явно указать, что источник не передан |
| Несколько складов в продажах | Продажи только «Алматы». Остатки SE есть по складам, берем свободный остаток | |
| Категории IEK | Префикс кода 1С (первые 4 цифры) | |
| Текущий остаток IEK | Остаток на 01.09.2026 − продажи 01–22.09; приходы за сентябрь неизвестны | Допущение |
| received/cancelled по поставкам | Все количества в «Пути» считаются подтвержденными открытыми | |

**Два источника продаж не сходятся.** Сумма строк накладных против помесячного отчета за 2025-01..2026-09: IEK — отчет примерно на 4% больше (кроме 06.2025, где в накладных есть «Петля» 210 000 шт, а в отчете нет); SE — отчет ≈ 50% накладных. У SE разрыв почти целиком в коробках (`030200192_`, `030200201_`, `030200193_`, `030200219_`, `030300014_`): в накладных крупные оптовые строки 36–90 тыс. шт, в отчете ровный ряд ~50 тыс./мес. Что именно включает отчет — вопрос к партнеру. Решение MVP: **накладные — основной источник спроса** (только в них есть строки для поиска разовых заказов), помесячный отчет — только **форма сезонности за 2024** (нормированный индекс, не уровень).

Номера накладных с префиксом `30…` (~5% объема) — другой тип/подразделение, пока учитываются как обычные продажи.

Грязь, которую чистят адаптеры:

- Последняя строка «Итого» в продажах и остатках — удалить. Колонка «Итого» в остатках IEK не является текущим остатком.
- Оставить только `Документ` начинающийся с «Расходная накладная». Количество > 0 — продажа, < 0 — возврат.
- Транзакции до 01.2025 единичные — для истории 2024 использовать `monthly_sales`.
- Коды 1С бывают без `_` и с префиксом `щт` — сравнивать как строки после `strip()`.
- Единицы: шт / м / упак. Не суммировать разные SKU.
- В SE «Ежемесячные продажи» есть отрицательные месяцы (возвраты).

## 3. Контракт (`app/schema.py`)

Источник истины — `app/schema.py`; здесь только обзор. Во всех таблицах ключ товара — `(supplier, sku)`, `supplier` ∈ {`IEK`, `SE`}.

| Таблица | Строк | Смысл |
|---|---|---|
| `sales_lines` | ~249 тыс. | Строка накладной: date, doc_id, qty (>0 продажа, <0 возврат), unit, warehouse |
| `monthly_sales` | ~100 тыс. | Помесячный отчет, 2024-01..2026-09 |
| `stock_monthly` | ~117 тыс. | Остаток на начало месяца (пусто = 0) |
| `stock_now` | ~3,6 тыс. | Свободный остаток на 22.09.2026; `source` = `manager_file` (SE) или `estimated` (IEK и SKU вне файла менеджера) |
| `in_transit` | ~300 | Открытые заказы с `eta` |
| `products` | ~3,7 тыс. | Справочник: name, unit, category (группа кода 1С), supplier_article, pack_multiple ≥ 1 |
| `seasonality` | 24 | Коэффициенты месяцев по компании для каждого поставщика |
| `manager_baseline` | 497 | Расчет менеджера SE для сравнения |
| `order_lines` | — | Выход движка: прогноз, страховой запас, остаток, в пути, исключенные разовые, дефициты, recommended_qty / final_qty, urgency, rationale, status |

`Params` в `schema.py` — все настраиваемые параметры и переключатели `use_*`. `schema.conform(df, TABLE)` проверяет колонки и приводит типы.

## 4. Расчет (движок)

Порядок: `oneoffs → stockout → forecast → replenish → explain`. У каждого шага свой флаг `use_*` — на них держатся тесты и демо «с фактором / без».

**Разовые заказы** (из полной архитектуры 5.1). Строка — кандидат, если `qty > median + k·MAD` по SKU (при MAD=0 — `qty > m·median`) и строка дает > X% месячного объема SKU. Кандидат исключается только если такой объем **нерегулярен**: SKU имел строки сопоставимого размера менее чем в `oneoff_min_months` разных месяцах. Исключенная часть заменяется на медиану (winsorize), а не удаляется. Сохраняется `doc_id`, score, reason. Факт продажи и расход склада не отменяются — исключение действует только на ряд регулярного спроса.
Контрольные примеры: IEK «Петля металлическая LOOP» 210 000 шт 09.06.2025 — должна исключаться; SE «Установочная коробка» 36–90 тыс. шт почти ежемесячно — не должна.

**Stockout** (5.2). Для stockout-месяца регулярный спрос = max(факт, сезонная оценка по доступным месяцам). Оценка маркируется как оценка (`stockout_uplift_qty`), в заказ второй раз не прибавляется.

**Прогноз.** Месячный регулярный ряд → сезонный индекс SKU, сжатый к профилю категории/компании при короткой или редкой истории → тренд по десезонированным последним 6–12 мес. с ограничением → внешний рост категории как отдельный слой только сверх выученного тренда (без двойного умножения). CatBoost в MVP не делаем.

**Пополнение** (4.1). `H = lead_time + review_period`.
`Q_raw = max(0, forecast_H + safety_stock − free_qty − in_transit_H)`, где `in_transit_H` — только поставки с ETA ≤ конец горизонта.
`safety_stock = z · σ_daily · √lead_time`.
`Q_final = 0` если `Q_raw = 0`, иначе `pack · ceil(Q_raw / pack)`.
Срочность: `days_of_cover < lead_time` → критично; `< H` → высокая; иначе плановая.
Позиция без данных (нет остатка/продаж) → `flags=needs_review`, а не ноль.

**Объяснение.** Шаблон из чисел, например: «Регулярный спрос 12 шт/день (исключен разовый заказ 210 000 шт от 09.06.2025; +18% за 2 мес. дефицита), сезонность окт ×1.24, на 37 дней нужно 520; есть 140 + в пути 100 → заказ 280 (кратность 20)».

## 5. Заказ и утверждение

`recommended_qty` неизменяем, менеджер правит `final_qty` с `override_reason`. Статусы: `draft → approved → exported`. Экспорт только утвержденного. Автоотправки нет. Экспорт XLSX/CSV по поставщику: Код 1С, Артикул поставщика, Наименование, Ед., Количество, Склад.

## 6. LLM (опционально, после 3:00)

Один провайдер из доступных ключей. На вход — fact pack строки или текущего заказа поставщика, без сырых строк продаж. Модель возвращает только выбранные идентификаторы фактов по строгой JSON-схеме. Приложение проверяет идентификаторы и формирует текст из фиксированного каталога; решение по количеству и предупреждение об оценочном остатке обязательны. Произвольный текст модели не отображается. Ошибка, таймаут, неполные данные или неподходящий ответ → шаблон. Модель по умолчанию `gpt-4o-mini`, явная настройка через `OPENAI_MODEL`, автоматического выбора по совпадению имени нет. Кнопки объяснения вызываются только пользователем; сводка использует итоговые количества менеджера. Ответы кешируются по фактам и модели.

## 7. Приемка (`tests/test_acceptance.py`)

На реальных данных с контролируемыми вмешательствами:

1. Увеличили `in_transit` SKU → `recommended_qty` не вырос, а при запасе — уменьшился. То же для остатка и роста категории.
2. SKU с выраженной сезонностью: прогноз на пиковый месяц > прогноза на спадовый.
3. SKU со stockout-месяцами: потребность с `use_stockout_fix` > без него.
4. Вкололи разовую строку ×50 медианы → рекомендация изменилась < 10%. Повторяющиеся крупные строки (SE «Установочная коробка») не исключены.
5. У каждой строки непустой `rationale`; группировка по поставщику дает ровно IEK и SE.
6. MOQ: `Q_raw=0 → 0`; иначе кратно `pack_multiple`.
