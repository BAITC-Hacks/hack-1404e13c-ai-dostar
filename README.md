# AI-Dostar: рекомендации по закупке

MVP для кейса «Электрокомплект»: очищает историю продаж IEK и Systeme Electric, оценивает регулярный спрос и рекомендует количество к заказу с учетом остатков, товара в пути, сезонности и кратности упаковки. Менеджер проверяет, при необходимости меняет количество, утверждает заказ и скачивает CSV/XLSX. Отправки поставщику из приложения нет.

## Запуск

Python 3.12+; на Windows команды ниже выполняются в PowerShell из корня репозитория.

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m app.adapters.build --raw datasets
.venv\Scripts\python.exe -m streamlit run app/ui/app.py
```

Для Linux/macOS замените `.venv\Scripts\python.exe` на `.venv/bin/python`. Исходные Excel партнера лежат в репозитории в `datasets/IEK` и `datasets/Systeme electric`; сборка создает `data/clean/*.parquet` (~8 с, в Git не входит). Вместо `datasets` можно указать папку с распакованными архивами партнера (`unzip -O cp866 … -d data/raw`, затем `--raw data/raw`). Рабочий интерфейс использует только реальные таблицы; при отсутствии данных предлагает выполнить сборку. Адрес после запуска: http://localhost:8501.

После загрузки данных настройте срок поставки по каждому поставщику, период пересмотра, уровень сервиса и рост выбранных категорий; переключатели позволяют включать и выключать факторы. Нажмите «Рассчитать». Вкладка «Заказ» показывает итоги, фильтры и таблицу для правки `final_qty` и причины. Если количество отличается от рекомендации, причина обязательна. Кнопка утверждения сохраняет заказ в локальный `data/state/approvals.json` (не входит в Git); экспорт содержит только утвержденные строки с положительным количеством. Повторный расчет с изменившимися исходными значениями требует нового утверждения.

Нулевая правка с причиной также сохраняется: исключённый товар не возвращается в заказ после перезапуска. Для положительных строк `needs_review` требуется результат проверки в поле причины. При оценочных остатках интерфейс предупреждает об источнике и просит подтвердить сверку со складом. «Сводка по заказу поставщика» учитывает итоговые количества менеджера. Причина правки включается в экспортное обоснование. Утверждение охватывает весь заказ выбранного поставщика, включая скрытые фильтрами строки. JSON защищён от одновременной записи сессиями одного процесса; несколько серверных реплик требуют отдельного хранилища.

Вкладка «Товар» показывает месячный спрос, прогноз и факторы расчета. Кнопка «Объяснить подробнее» использует LLM, если задан `OPENAI_API_KEY`, а без него возвращает проверенное шаблонное объяснение. «Проверки» пересчитывает выбранный SKU с выключенными факторами и дополнительным товаром в пути; «Сравнение с менеджером» сопоставляет расчет для SE с исходным файлом менеджера; «Разовые заказы» показывает исключенные из регулярного спроса строки. Сценарий показа — [docs/demo.md](docs/demo.md).

Карточка доступна для всего каталога, включая товары без текущей рекомендации. На графике отмечены разовые продажи и месяцы оценённого дефицита. Прогноз горизонта распределяется по будущим дням месяцев и не является прогнозом полного месяца. Сравнение SE показывает фактический и регулярный средний спрос за 12 полных месяцев, период указан над таблицей; сортировать можно по расхождению спроса или заказа.

## Данные и методика

Движок расположен в `app/engine/`, единый вызов — `app.pipeline.run()`, контракт таблиц — `app/schema.py`. Адаптеры в `app/adapters/` преобразуют Excel в `data/clean/*.parquet`. Подробнее: [архитектура MVP](docs/architecture.md), [спрос](docs/methodology-demand.md), [прогноз и расчет заказа](docs/methodology-forecast.md).

Порядок расчета: разовые строки накладных → оценка спроса в месяцы дефицита → сезонность и тренд → страховой запас и количество заказа → объяснение. Для разовых строк сравнивается размер строки с медианой/MAD по товару, ее доля в месяце и повторяемость больших строк. Сезонный профиль SKU с короткой историей смешивается с профилем категории и компании. Количество заказа округляется до кратности поставщика. Числа и причины сохраняются рядом с рекомендацией; окончательное решение остается за менеджером.

Конкретные параметры: кандидат в разовые продажи превышает `median + 5 × 1.4826 × MAD` (при MAD=0 — `10 × median`) и 30% продаж месяца; повторение сопоставимого опта в трёх месяцах сохраняет его в спросе. Избыточный объём срезается до типичной строки. При дефиците используется медиана минимум двух месяцев с положительным остатком с поправкой на сезонность и число наблюдавшихся дней. Прогноз использует 12 полных месяцев; сезонность сжимается SKU → группа → компания и ограничена 0.4–2.5, устойчивый тренд — 0.8–1.25. Горизонт `H = срок поставки + период пересмотра`, страховой запас `z × σ × √срока`, заказ `max(0, прогноз_H + страховой − свободный остаток − приход до H)` с округлением вверх до кратности. Подробные формулы и исключения — в двух методиках выше.

Ограничения входных данных: нет идентификатора клиента, цены, точных периодов отсутствия товара, подтвержденных сроков поставки и BOM. По IEK текущий остаток оценен из остатка на начало сентября за вычетом продаж; неизвестные поступления могут повлиять на рекомендацию. У SE помесячный отчет о продажах существенно расходится со строками накладных, поэтому накладные являются основой уровня спроса, а отчет 2024 года используется для формы сезонности. Сравнение с менеджером показывает пустой `manager_order` как отсутствие эталонного заказа, а не как ноль. Подробные допущения — в [docs/architecture.md](docs/architecture.md).

`datasets/` содержит исходные книги партнера без изменений и их CSV-копии (`*_CSV`, создаются `scripts/excel_to_csv.py`; расчет их не использует). Адаптеры находят книги по ключевым словам в имени файла, поэтому имена должны соответствовать содержимому. Сборка из `datasets/` проверена: все 8 таблиц совпадают со сборкой из архивов партнера.

## Проверка

```powershell
.venv\Scripts\python.exe -m pytest -q
```

Тесты расчетного движка, адаптеров и сценариев продукта выполняются без платного API. Файлы `.env`, `data/raw`, `data/clean` и `data/state` исключены из Git.

`tests/test_ui_real.py` проверяет реальный pipeline, пять вкладок, LOOP, семь сценариев факторов, пустую причину, нулевую правку, утверждение, оба экспорта и новую сессию. Файл утверждений изолирован во временной папке. Перед тестами обязательно выполнить сборку Excel, иначе тесты реальных данных будут пропущены. Дополнительная проверка браузера при запущенном сервере: `pip install playwright`, затем `python scripts/ui_browser_smoke.py` (нужен установленный Microsoft Edge); снимки сохраняются в `.pytest_cache/ui-screenshots`.

Оставшиеся задачи расчёта и уточнения исходных данных с владельцами перечислены в [плане завершения](docs/completion-plan.md). Проходящие тесты не закрывают отмеченное там расхождение критерия приемки №4.
